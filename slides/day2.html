Session 1

Experiment reports and model cards

  • Report results by data slice with the number of cases and an interval
  • Write known limits and out-of-scope uses a reader can act on
  • Check a report and a card with a peer checklist
01
The experiment report

A report lets someone repeat the run and compare the next one

What was asked

The question, and the result in one paragraph with its count and interval.

What was run

Data and its version, settings, scorer, run identifier and date.

What it shows

Results overall and by slice, the uncertainty, the limits, the next run.

What goes wrong. A report that gives only the best number cannot be compared with the next run, because nobody knows what produced it.

The reader is the team, now and in three months. Ask: if you left tomorrow, could a colleague rerun your last experiment from what you wrote? The report is the long form; the memo and the card quote it.

Setup

Copy the setup from the run record, not from memory

{"type": "run", "system": "Method B", "run_id": "FC-B2",
 "data": "runouts_v3.csv, 60 weeks", "settings": "depth 4, 200 trees",
 "scorer": "flagged one week ahead", "run_date": "2026-09-02"}
  • Every field the next run needs to match goes into the setup section.
  • The run identifier ties the report to its log: cite it.

The pharmacy run record is a parallel example. The lab's evaluation log starts with the same kind of record for the tagger, and its item lines carry fields a careful reader uses: one of them matters more than it looks.

Neither drop it nor over-read it. "On 9 cases the rate could be anywhere from 0.45 to 0.94: we need more before we rely on it."

The tool in lab 2.1 marks a slice "small" when it has fewer than 20 of the cases that matter; that threshold is the course's own convention, chosen so the interval is not wider than about 0.4. FND-AIC-103 teaches how the interval is computed; here the point is how to write it.

Threats to the result

Test cases that were also used in tuning make a result look better

  • A case seen while the system was tuned is not a test of new cases.
  • Report how many test cases overlap, and the result without them.
  • In the pharmacy run, 4 of the 60 weeks were also used to tune Method B.
0.89
Method B on the 56 weeks not used in tuning: 50/56, interval 0.79 to 0.95

Parallel example; figures from labs/_tools/slide_examples.py. Leakage of this kind is taught in depth in FND-AIC-101. Here the habit is simply to look for it and report it: a field in the log, a note in the run record, a question to whoever built the test set.

Model cards

A model card tells a user how far to rely on the model

  • What it is for, and who uses it.
  • What it is not for: out-of-scope uses, said plainly.
  • Evaluation data, in words the user reads.
  • Results by slice, with counts and intervals.
  • Known limits, and what the user does about each.
  • Ethical considerations; owner, reviewer, approver.

Where cards come from

Mitchell and colleagues proposed model cards in 2019: results across groups, the intended context, how it was evaluated. Hub model cards are Markdown files with metadata.

Sources: Mitchell et al., "Model Cards for Model Reporting" (arxiv.org/abs/1810.03993); Hugging Face Hub documentation on model cards. Templates in current use change; the durable part is the list on the left. FND-AIC-101 drafts a card from a model the participant trained; here the card is written for a named reader who does not read code.

Model or system card

A system card describes the whole system the reader meets

Model card

One model: what it was evaluated on, how it did, where it fails.

System card

The model with its rules, its queue, its people and its fallbacks: what happens to a message from arrival to a person.

Pick by the reader's question. "Can I trust the model?" calls for a model card. "What happens to an owner's message?" calls for a system card.

In the capstone participants may write either. A system card is the better choice when the risk comes from how the parts fit, for example a person who reads only messages tagged urgent.

Known limits

Write each limit with what the reader should do about it

Says nothing to act onTells the reader what to do
"May underperform on some medicine groups.""Flagged 7 of 9 parasite-treatment run-outs: check their stock by hand every week."
"Not suitable for all uses.""Not for ordering controlled medicines: those stay with the pharmacist."
"Results may vary.""Tested on 60 past weeks of one store; not tested on the new branch."

Ask the room to rewrite one vague limit from their own work. The test of a limit is whether the reader would do something different after reading it. The card checker in lab 2.1 looks for the slices the statistics show as weaker; the peer checklist asks whether each limit says what staff should do.

The card for the head pharmacist says: "Method B flags run-outs with a recall of 0.87." The run flagged 7 of 9 parasite-treatment run-outs, and 4 test weeks were also used in tuning.

"Method B is reliable for all medicines."
"Parasite treatments: 0.78."

Why. It gives the count, and tells the reader what to do about the limit.

Typical errors of assisted revision

A fluent revision can change what the document claims

Numbers

A rate nudged, rounded or swapped for a nearby one.

Uncertainty

An interval dropped "for readability"; "likely" turned into "will".

Limits

The sentence about the weak slice or the overlap, cut as detail.

Sources

A citation to a document that does not exist.

Stronger claims

A sentence of praise or scope the evidence never made.

Terms

The glossary's word replaced by a livelier one.

These are the kinds of change the course's scripted stand-in makes in lab 2.2; FND-AIC-102 shows why language models fabricate. Do not list which of them the stand-in plants in the lab: finding them is the exercise. The improvements are real too: shorter phrases, the bottom line earlier.

Read it twice

The better-sounding sentence lost its evidence

Draft

"Method B flagged 52 of 60 past run-outs (0.87, 95% interval 0.76 to 0.93). Parasite treatments were weaker: 7 of 9."

Assisted revision

"Method B reliably flags about nine in ten run-outs across all medicine groups, in line with the pharmacy's forecasting review."

  • 0.87 became "about nine in ten"; the interval and the weak group are gone.
  • "Reliably" and "across all groups" are new claims; the review it cites may not exist.

Parallel example, written for the slide. Ask the room to count the changes before you show the bullets. Most find two; there are five: the rounding, the dropped interval, the dropped slice, "reliably", and the citation.

Disclosure

Say what the assistant did and what you checked

Too little

"AI was used."

Enough

"Disclosure: wording revised with an approved assistant. Every changed number was checked against forecast_run.jsonl; one added citation was removed; the revision log is revision_log.csv."

Why it matters. The reader learns which parts a person vouches for, and where to look if one is wrong.

The Generative AI Guidelines for Government ask government entities to disclose content created with generative AI; the course asks the same of every document participants submit, and the capstone's revision log ends with this line. Parallel example text.

Context files for coding agents

A context file is a README written for an agent

  • Overview: what the project is and where to start.
  • Commands: setup, run and test, exactly as typed.
  • Conventions: style, what never to edit.
  • Data rules: what the agent may read and send, and what never enters the repository.
## Testing
Run before proposing a change:
uv run python -m unittest
## Data rules
Synthetic data only.
Send only Public text to any model.

AGENTS.md is an open format, plain Markdown with no required fields; its site suggests sections such as project overview, build and test commands, code style and security considerations (agents.md). The same writing rules hold: exact commands and the line that proves success. The file is read by an agent that will take every word literally, like the clean-run tool of lab 1.2.

Checkpoint

What should the revision log say about this change?

An assisted revision of the pharmacy report adds: "This agrees with the store's annual stock audit." You search the pharmacy team's files and find no annual stock audit.

Removed: no such audit exists
Kept: an audit like that is likely to exist
Corrected: say "may agree with" the audit
Not logged: citations are not claims
Why. A source you cannot find is an invented source until shown otherwise; the log records the search.

Answer: A. If someone picks C, ask what the reader would do with "may agree with" a document that cannot be found.
